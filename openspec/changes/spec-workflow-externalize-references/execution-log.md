### pruner 裁剪窗口实测（本变更核心验收证据）

一手核实（不依赖记忆）：插件 `dsh-compaction-tool-result-pruner` 默认 `thresholdChars 8192 / headChars 4096 / tailChars 1024`，`dsh-base/cordis.patch.yml` 正以该三值挂载；计数函数 `codePointLength = Array.from(text).length` 即**码点**（与 `python3 len()` 同口径）；超阈值时中段替换为标记 `\n\n[... tool result middle pruned ...]\n\n`（39 码点），仅保留头 4096 + 尾 1024（源码 `lib/index.js:8,12–13,111`；配置校验 `:43–44` 亦按 `headChars + marker + tailChars ≤ thresholdChars` 计）。

模拟结果（**与早前实测 23.9% 存活率精确吻合 → 模型可信**）：

| pruner 裁剪后是否仍可见 | 外移前 | 外移后 |
| --- | --- | --- |
| Read-next 路由表（§一） | ✗ | **✓（新增）** |
| 三个 references 指针 | ✗ | **✓（新增）** |
| 全局纪律·固定承诺（§一） | ✓ | ✓ |
| §十二 三条红线 + 「绝不做」段 | ✓ | ✓ |
| §七 恢复协议（含「三方对齐」） | ✗ | ✗（**未达项**） |
| 裁剪窗口 | 5120 / 21464 = 23.9% | 5120 / 15829 = **32.3%** |

- 口径：5120 = 纯头 4096 + 尾 1024 码点；**含替换标记则为 5159**。比例上升的**唯一原因是分母缩小**（绝对存活量不变）——本变更对 pruner 绝对存活量零增益。真实收益是「外移前根本没有、裁剪后仍持有」的**路由表与 references 指针**（结构能力），以及三个 references 各自 <8192、单独加载不触发裁剪。彻底解法仍是第二步压 ≤8192（按渲染后口径）。
- 达成：裁剪后会话**仍持有路由表与 references 指针**（外移前根本没有此表）→ Scenario「外移内容可按需读取」在裁剪态下仍可达，这是本变更的核心收益。
- **未达（如实记录，非回归）**：§七 恢复协议、§十 接续流程位于被裁剪中段，裁剪后不可见；缓解事实是头窗口保留了 §一「状态载体 = 工件（唯一权威进度源）+ 勾选态 + 提交历史」表，裁剪态仍知道进度源在哪。
- **另一条路径（机制更正后补记）**：压缩（compaction）不是裁剪而是**表层 `replace` 整块遮蔽**——被遮蔽范围从派生历史消失，存活率只有 0% 或 100%；正文滑出保留尾部（`retainTokens ≈ (W−O)×0.16`）即被摘要替换，tail 窗口救不了。该路径下入口**文件层**仍完整（磁盘文件未变），恢复靠压缩摘要 + 重读入口。详见第六节。

### 三条更正定性

1. **「`/compact` 后仅存活 23.9%」因果不成立**（原 proposal.md Why 节表述）：`/compact` 不触发 pruner；23.9% 是「会话压力越阈时，pruner 对 `skill` 工具 tool result 的裁剪几何」。**已在 proposal.md / design.md 更正**。

3. **比例回升是分母效应**：绝对存活量 5120（含标记 5159）不变——第一步外移对 pruner 存活量零增益；比例上升只因入口总量变小。第一步的真实收益是**结构能力**，不是存活量。

# Design

## Context

SKILL.md 现为 12 节单文件、21464 Unicode 码点；本部署模型会话组合启用 `dsh-compaction-tool-result-pruner`（阈值 8192 码点，头 4096 + 尾 1024），压缩后中段（§四后半～§十二主体）丢失。动机与平台事实链见 `proposal.md` Why 节。本设计只覆盖两步节奏的**第一步**：纯剪切外移 + 按需读取行为验证；第二步（去重改写、压 ≤8192 硬线）另立变更。

## Goals / Non-Goals

**Goals:**

- 三块自包含内容按消费时机外移为 references，入口降至约 14000 码点（数字记录在案）
- 入口在压缩后仍保留全部红线内容：恢复协议、全局纪律、红线级失败条目、Read-next 路由表
- 外移为纯剪切：行为语义零变化、frontmatter 逐字节不变、12 节结构保持（节号不断链）
- 用本变更自身的执行自举实测「会话是否真按路由表读 references」

**Non-Goals:**

- 不做去重/合并/改写性压缩（授权改写归第二步变更）
- 不动 §五/§六/§八/§九/§十 的正文（第一步不动这些节）
- 不拆多顶层 skill、不改命令薄壳与映射文件 schema

## Decisions

### D1：外移对象与文件布局（按消费时机）

| 现节 | 码点量级 | 第一步去向 | 消费时机 |
| --- | --- | --- | --- |
| §十一 模型路由（含自检脚本、白名单表、三档回退） | 3609 | **→ `routing.md`** | 派发子代理前读 |
| §十二 边界与失败处置表（红线级条目除外） | 2556 | **→ `failure-modes.md`** | 异常处置时读 |
| §四 并行派发提示模板 + 串行模式细节 | ~1000 | **→ `planning.md`** | 阶段 1 派发时读 |
| 其余各节（含 §四骨架、§七恢复协议全文） | — | 留入口 | 恢复/日常 |

- 入口在总览附近新增 **Read-next 路由表**（三行：派发规划线前读 planning.md；派发任一子代理前读 routing.md 并跑其中自检；异常/边界情形读 failure-modes.md）。
- §十一/§十二在入口留**摘要段**（各 ≤10 行）：§十一留「路由键表 + 三档回退顺序 + vision 规则」一句话级要点；§十二留**红线级条目**（违反即致不可逆/失控/静默假设者，如：绝不副作用创建 openspec/、不得静默把待决项变假设、不提交未过审或未验证内容、DELEGATED_CALLER 是平台设计不是故障、auto 硬停四条件）。
- **备选与否决**：A 线主题横切 4 文件（execution.md 一并外移）——§八执行引擎属压缩丢失区且 continue 恢复即需，第一步外移收益为负；B 线会话两册——恢复协议随执行册外移恰落入丢失区。两者均留待第二步在 8192 硬线约束下重估。

### D2：纯剪切与节结构保持

- 12 节标题与节号**全部保留**，仅三处节内瘦身（§四/§十一/§十二），既有「见第 X 节」交叉引用（§十一被引 8 次、§四被引 7 次）在入口内**继续有效**；只有指向被外移内容的引用改为文件指针（「第十一节」→「`routing.md`」），逐一映射、逐一验证。
- 外移文件内部引用回入口时写「SKILL.md 第 X 节」；dsh/README.md:193 的「第十一节」提法同步改为 `routing.md`。

### D3：横切内容单一权威源

- §四中转协议全文**留入口**（第一步不动 §四主体，只外移模板）——它被 §五/§八/§十二引用，是最高频横切点。
- 模型路由的唯一权威源 = `routing.md`；入口摘要段只写要点 + 指针，**不复制展开细节**（防双源漂移；验证句保证关键内容唯一存在于 routing.md）。

### D4：验证方法（结构化，硬线归第二变更）

1. frontmatter `name`/`description` 逐字节一致（diff 仅正文）。
2. 引用闭合：三个 references 文件存在且非空；入口与外移文件互引的每个相对路径 `test -f` 通过；同步后 `dsh/README.md` 无「第十一节」残留。
3. 内容无损：外移前 §十一/§十二/§四模板的关键词（`三档回退`、`parallelism`、`fallback`、`DELEGATED_CALLER`、`重派一次` 等）在外移后唯一命中所属 references 文件。
4. 码点记录：`python3 len()` 记录外移后入口码点（预期 ≈14000），写入本变更执行记录。
5. 加载冒烟：会话内 `skill` 按名加载成功、`read` 读取 references 成功、命令面板 `/spec-flow` 出现。
6. **自举行为验证**（第一步核心目标）：本变更阶段 3 执行时，派发任务前是否实际读取 `routing.md`、异常时是否读取 `failure-modes.md`——执行轨迹记录在案，作为第二步变更的决策输入。

## Risks / Trade-offs

- [模型漏读 references（最高风险）] → 入口 Read-next 路由表 + 关键数字内联（≤5 问/轮、parallelism=3、三档回退顺序）+ D4.6 自举实测；若实测漏读率高，第二步变更重估形态（回撤或收窄外移面）。
- [双源漂移：入口摘要 vs routing.md] → D3 单一权威源 + 验证句保证展开细节唯一存在于 routing.md。
- [引用断链] → D2 节结构保持，引用改动仅指针类且逐条验证（grep 白名单外零残留）。
- [opencode 侧多文件按需加载未实测] → 记录为已知缺口，不阻塞（Agent Skills 标准同构，聚合层 symlink 实时视图两栖）。
- [中间态入口 ≈14000 码点仍超 8192 阈值] → 用户已接受（两步节奏决策）；红线内容已在入口，压缩丢失面较现状收窄。

## Migration Plan

- 单提交批次实施（见 tasks.md）；回滚 = `git revert` 对应提交并删除三个 references 文件（bundle 内文件无 skctl 登记依赖，无宿主操作）。
- 部署即时生效：local 源为目录级 symlink，宿主侧聚合层实时视图，无需重装或重启（SKILL.md §十二既有实测结论）。

# 交付审核(Delivery Self-Review)

## 概述

把交付物发出去之前，按统一标准自查一遍：**收集依据 → 盘点分流 → 逐类审核 → 分级 → 结论 → 落盘报告**。

覆盖对象：图片/截图、Office/PDF 文档、数据报表、代码工程包（代码包只审文案与敏感信息，**不审代码逻辑与功能**）。

核心原则：

- **依据三层合并**：本次对话要求 > 交付目录旁的 `DELIVERY.md` > 本 skill 的 [checklist.md](checklist.md)，并集合并；冲突时高层为准并在报告中注明
- **敏感信息硬规则永远生效**，不受任何清单增删影响（见下方硬规则表）
- **只报告不修复**：审核阶段绝不改动交付物
- **范围透明**：跳过的文件必须在报告「审核范围」中列明

## 何时不使用

- 单个文件的琐碎检查（如“看下这个 md 有没有错别字”）—— 直接读文件处理即可
- 代码逻辑/功能/架构审查 —— 使用 `requesting-code-review` 流程

## 审核流程

### 1. 收集依据

按顺序收集，三层取并集：

1. **本次对话**中用户明确给出的需求/验收要求
2. 交付目录内或其项目根（git 根）的 `DELIVERY.md`（存在则读取）
3. 本 skill 的 [checklist.md](checklist.md)

敏感信息硬规则**独立于上述三层**，永远执行。

**注意区分两类文件**：`DELIVERY.md` 是**验收规范**（第二层依据）；交付目录内的交付清单类文件（如 `交付清单.md`、README 里的文件列表）**只用于「清单承诺 ≠ 实物」的完整性核对**，不作为验收标准 —— 除非用户在本次对话中把它指定为依据。

某层不存在时跳过该层即可，但要在报告「依据来源」中注明**实际生效的层级**。

### 2. 盘点与分流

先完整列出交付目录所有文件（含隐藏文件、递归子目录），再按类型分流：

| 类型 | 扩展名 | 处理方式 |
|---|---|---|
| 图片 | png/jpg/jpeg/gif/webp/bmp/svg | 派发 `vision` 子 agent，每批 ≤10 张、多批并行（提示词带上文与检查维度） |
| PDF | pdf | Read 工具直接读取；页数多时分段读 |
| Office | docx/xlsx/pptx | 运行 `scripts/extract_office.py` 提取文本后审核 |
| 代码/工程 | py/js/ts/java/go/… 及工程目录 | 只查敏感信息、调试残留、垃圾文件、清单齐全性 |
| 其他/二进制 | zip/psd/exe/… | 无法审阅的列入「审核范围」跳过并说明原因 |

运行脚本（零依赖，标准库实现）：

```bash
~/develop/docker/run.sh python "python <skill目录>/scripts/extract_office.py <交付目录>"
```

若交付目录不在 `~/develop` 下（docker 容器看不到），用宿主机 `python3` 运行同一脚本（零依赖，结果一致）。

**范围规则**：直接全审、零前置交互；仅当文件数 >200 或明显混入大量无关内容时，暂停向用户确认范围。

### 3. 逐类审核

- **图片**：派发 `vision` 子 agent 检查 ① 占位符/草稿残留（Blocker）② 文字错误、乱码（Major）③ 模糊/变形/裁切（Major）④ 敏感信息（按硬规则）⑤ 格式规格（仅当依据中有明确要求才查）⑥ 同批多图风格一致性（Minor~Major）。
  图片处理降级顺序：**vision 子 agent → Read 直接查看图片**（当前运行时不支持派发子 agent 时）→ 列入「审核范围」跳过并说明（连图像内容都无法获取时，须在对话汇总中提示图片未审）。实际采用的方式要写进「审核范围」。
- **文档/报表**：逐条对照依据清单；特别注意占位符、错别字、跨文件信息矛盾、表格数据串位、文档属性/批注/演讲者备注中的内部信息（`extract_office.py` 会一并输出）
- **代码包**：敏感信息（硬规则）+ 调试残留（print/console.log、注释掉的大段代码、TODO/FIXME）+ 垃圾文件（`.DS_Store`、`~$*`、`*.bak`、`.env`、`node_modules/`）+ 有交付清单时核对文件齐全性。**不审代码逻辑**
- **通用质量**：逐条执行 [checklist.md](checklist.md) 全部适用项

### 4. 问题分级

| 级别 | 定义 | 示例 |
|---|---|---|
| **Blocker** | 交付事故，发出前必须解决 | 密钥/个人信息泄露、清单承诺的文件缺失、占位符未替换 |
| **Major** | 专业质量缺陷，应修复 | 错别字、跨文件信息矛盾、垃圾/临时文件混入、内网 IP(待人工确认) |
| **Minor** | 建议改进，不影响交付 | 命名不规范、术语不统一、重复文件、格式细节 |

每条问题必须附：文件路径（文档类尽量带行号/章节）、问题描述、证据（原文引用或图片问题描述）、修复建议。

### 5. 结论判定

| 结论 | 条件 |
|---|---|
| **不通过** | Blocker ≥1，或 Major >5 |
| **有条件通过** | 0 Blocker 且 Major 1~5（报告列明“交付前必须解决项”） |
| **通过** | 0 Blocker 且 0 Major（Minor 仅记录） |

### 6. 报告落盘与汇总

- 按 [report-template.md](report-template.md) 生成报告，写入交付目录 `delivery-review-report.md`（简体中文）
- 报告头部必须写明依据来源与结论；附「审核范围」表（已审 + 跳过及原因）
- 对话内输出简短汇总：结论 + Top 问题 + 修复顺序建议
- 提醒用户：打包交付前排除 `delivery-review-report.md`
- **审核结束即止**：不生成 TODO 文件、不自动修复交付物

## 敏感信息硬规则（永远执行，优先级最高）

| 类别 | 匹配内容 | 级别 |
|---|---|---|
| 凭证密钥 | 私钥（`BEGIN * PRIVATE KEY`）、AK/SK、`api_key=`/`token=`/`password` 赋值 | **Blocker** |
| 凭证文件 | `.env`、`id_rsa`、`credentials`、`.npmrc` 出现在交付包 | **Blocker** |
| 个人信息 | 手机号、身份证号、个人邮箱、个人账号 | **Blocker** |
| 网络内部信息 | 内网 IP（10.x / 172.16-31.x / 192.168.x）、`.internal`/`.local` 域名、内部系统 URL | **Major**（附“若为刻意内容请人工确认”） |
| 个人路径 | `/home/<用户名>`、`C:\Users\<用户名>` | **Minor** |

排查建议：对文本类文件批量检索关键词（`password`、`secret`、`key`、`token`、`10.`、`192.168.`、`/home/`、`/Users/`），图片/截图由 vision 子 agent 一并检查界面中的敏感信息。

## 常见错误（红旗）

- 跳过依据收集直接开审 —— 必须先收集三层依据，并记录来源到报告头部
- 只列问题、不列通过项 —— 报告必须包含全量检查项汇总表
- 只做单一类型检查 —— 图片/文档/代码必须按分流表全部覆盖
- 跳过文件不说明 —— 「审核范围」表必须列出跳过项与原因并标 Minor
- 替生成逻辑辩护 —— 发现版块内容与定位矛盾（如「待关注领域」出现正面描述）时，不得以「系统按设计就是这样输出的」为由放过；审核对象是最终呈现，不是生成流程
- 声称无法审图就整类跳过 —— 先尝试 vision 子 agent，再尝试 Read 直读；两者都不可用才可跳过并在报告中说明
- 审核中顺手修了交付物 —— 只报告不修复，修改永远留给用户
- 用自定义分级（如 P0/P1）—— 必须使用 Blocker/Major/Minor 与固定阈值

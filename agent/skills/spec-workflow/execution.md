本文件为 SKILL.md 第八节「执行双引擎与三模式」中两个引擎小节的外移正文；回入口引用写「SKILL.md 第 8 节」。

**subagent 引擎（默认）**：

- 每个任务一个 **fresh** 子代理（不要用继承上下文的 fork；只有 fresh 支持模型选择）。
- 提示自包含（缺一不可）：项目根绝对路径、**任务原文（含编号）**、**design.md 中该任务所属组的实现要点逐字引用**（不得转述）、验收标准=**验证句原文**、写范围（允许改的文件/目录，须含该任务触达面条目所列文件）、禁止事项（不 `git add`/`git commit`、不改 `tasks.md` 勾选、不改写范围外文件、不跑破坏性或不可逆命令）。
- 组内并发派发、**组间串行**；并行上限取映射文件 `parallelism`（默认 3）。
- 回执格式要求：改动文件清单、验证命令与输出摘要、偏差与未完成项、**待决问题（TOP 待决项）**。按 [routing.md](routing.md) 给任务子代理应用 `apply` 路由（任务需读图时改用 `vision` 路由）。
- **待决问题中转**（第四节协议）：子代理遇需用户拍板的决策不得自行假设，在产物与回执中上浮 → 主会话**立即代问用户**（≤5 问/轮）→ 把**上一轮回执摘要 + 用户答复**并入新提示**接续重派**（上下文重建，非同一实例）。**这正是让 subagent 事实上能与用户交互的机制**：子代理自身不能提问（`DELEGATED_CALLER`），问题与答复经主会话中转。
- 核对不通过：auto 模式 → 派发修复子代理（附失败输出）后重新核对；step 模式 → 向用户呈现问题与证据等裁决（见 [failure-modes.md](failure-modes.md)「审核被拒」）。

**team 引擎（可选，实验性 Agent Teams）**：

- 仅 `--engine team` 或映射文件显式启用时使用；否则不启用。成员创建失败或不可用时按 design「风险与回退」**降级为 subagent** 完成该任务。
- 主会话作为 Lead：用任务板工具（挂载 Agent Teams 时 Lead 可见 `team_task_create` / `team_task_list` / `team_task_get` / `team_task_update`，以当前会话实际挂载的工具名为准）把组内每个任务发布到**共享任务板**，卡片含任务原文、**验证句**、写范围、产出要求。
- `spawn_teammate` 创建具名 implementer，**成员数 ≤ 组内任务数**（并受 `parallelism` 封顶），成员按卡片 `owner` 认领执行；用 `list_agents` / `wait_agent` 观察。
- **审核反馈走消息**：`send_message` 把修改要求发给负责该任务的成员，由其在同一上下文内修复（保留其上下文，不重派新成员）。
- **待决问题中转**（第四节协议）：成员上浮的待决项由 Lead **立即代问用户**，再用 `send_message` 把答复**回送同一成员**（上下文保留、可多轮往返澄清）——与「审核反馈走消息」同一条通道。**这是让被拥有的 teammate 事实上能与用户交互的机制**（成员自身同样不能直接提问）。
- 成员卡死或创建失败：`interrupt_agent` 中断后重建；无法恢复则降级 subagent 完成该任务。
- 该引擎**忽略 `apply` 路由键，阶段级模型路由整体不适用**（teammate 创建工具无模型参数，fork teammate 锁定 Lead 模型）。

## 附：三模式与提交纪律、硬停条件（自 SKILL.md §八 外移）

**三种执行模式与提交节奏**：

| 模式 | 停留点 | 提交时机 | 提交信息示例 |
| --- | --- | --- | --- |
| `auto` | 不停留（除下方硬停条件） | 全部任务完成后提交一次 | `feat(<scope>): 完成 <change> 实现` |
| `step-task` | **每个任务**核对后停留审核 | 每批次审核通过后提交一次 | `feat(<scope>): 批次 N <组名>` |
| `step-group` | **每个批次（组）**核对后停留审核 | 每批次审核通过后提交一次 | 同上 |

- 停留时展示变更摘要：批次号、任务号、改动文件、验证输出摘要、diff stat，然后等用户确认（继续 / 修改 / 停止）。
- 提交纪律：只 `git add` 本批次涉及的文件（含 `tasks.md` 勾选）；不提交密钥、构建产物、日志、临时文件；批次提交信息**含批次号**。
- `auto` 模式的**硬停条件**（必须停下来问用户，不得自行推进）：①不可逆操作（删除/覆盖/force push/数据迁移/发布上线）；②安全敏感（凭据、密钥、权限、生产配置）；③工作区外副作用（改宿主文件、其他仓库、重启容器或服务）；④计划彻底失效（实现与 design/spec 前提矛盾）。除此之外 auto 不在任务之间询问「是否继续」。
- 任务失败：**重试一次**（同一提示 + 上次失败输出摘要）；仍失败则**暂停本批次并报告**（任务号、错误摘要、已完成/未完成清单、建议），不中断整个流程、不擅自动其他批次。


## 附：验证与归档派发要点（自 SKILL.md §九 外移）

1. **先读目标项目声明的验证方式**：项目根 `AGENTS.md` / `CLAUDE.md`（其次 `README`、`package.json` scripts、`Makefile`、CI 配置）。项目声明优先于通用猜测。
2. **执行验证**：可派 **fresh** 子代理执行（按 [routing.md](routing.md) 应用 `verify` 路由），提示自包含（项目路径、要跑的命令、期望结果、只读约束），回传命令与输出摘要；失败必须回传关键错误段。聚合多个命令时逐条记录退出码。
3. **验证不通过 → 不归档**。报告失败证据（命令、输出、涉及任务），问用户：修复（回到阶段 3 派修复任务）或明确跳过（记录为已知缺口，需用户显式批准后才继续）。
4. **通过后归档**：确认 `tasks.md` 全部勾选（有未勾选项不得归档），加载 `openspec-archive-change` skill 执行归档并同步主规格。
5. **归档单独提交一次**（`docs(openspec): 归档 <change>`），不与批次改动混提。归档报错 → 贴错误原文并停，不手工搬移目录。
6. **最终汇报四要素**：①变更名与工件路径；②验证证据（命令 + 结果摘要）；③归档位置（`openspec/changes/archive/...` 与同步后的主规格）；④后续宿主操作清单（需要用户在容器外做的事，如 skctl 登记、推送 `git push`、以及命令仍不可见时的 `docker compose restart dsh` 兜底——本流程不代劳）。

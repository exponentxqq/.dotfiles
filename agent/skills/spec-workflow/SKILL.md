# spec-workflow 固定工作流

本 skill 是**执行手册**，不是建议：每一步按本文执行，未写到的情况回到用户。本文件面向**没有本次对话上下文**的未来会话——不要假设你记得任何前情，一切从工件与命令输出重建。

## 一、总览

五阶段流水线，入口为用户级斜杠命令 `/spec-flow`（命令薄壳加载本 skill）：

```
阶段1 独立双线规划 → 阶段1.5 差异收敛与分歧复算 → 阶段2 落档（工件） → 阶段3 执行（双引擎/三模式） → 阶段4 验证与归档
     line-a + line-b          diff-matrix + 第三线复算        openspec-propose     subagent | team          openspec-archive-change
```

阶段 1.5 = **差异收敛与分歧复算（三分类 + 复算 + `grill-me` 设计树/前沿分轮）**：双线交叉比对归为共识 / 分歧 / 单边遗漏、可查证分歧自行裁定、无法查证的分歧派第三线复算——这套裁定与留痕逻辑不因提问方法而改变；**只有「怎么问」遵循 `grill-me` skill 的设计树/前沿分轮法**（第五节）。

**状态载体 = 工件（artifact is state）**：

| 载体 | 路径 | 作用 |
| --- | --- | --- |
| OpenSpec 变更工件 | `openspec/changes/<change>/{proposal.md,specs/**,design.md,tasks.md}` | 唯一权威进度源 |
| 任务勾选态 | `tasks.md` 的 `- [ ]` / `- [x]` | 逐任务完成度 |
| 提交历史 | `git log` | 每批次/落档/归档的凭证 |
| 规划中转材料 | `/tmp/spec-flow/<change>/{line-a.md,line-b.md,diff-matrix.md}` | 仅本流程临时使用，易失、不入库、不进提交 |

固定承诺：

1. **阶段边界必汇报**：每阶段结束输出简短摘要（做了什么、产物在哪、下一步），不静默跨阶段。
2. **规划外 scope 变化回到用户**：需求扩张、发现要改其他仓库/其他变更、要动不可逆操作——停下问，不自行扩大范围。
3. **不假设未给出的选项**：见第三、七节，一次只问该阶段需要的。

参数面（`/spec-flow` 与命令薄壳同源）：

| 参数 | 含义 | 缺省行为 |
| --- | --- | --- |
| `<需求描述>` | 新建流程的需求原文 | 为空则开放式询问「要做什么」 |
| `continue <变更名>` | 接续未完成变更（第十节） | — |
| `--parallel` | 阶段 1 两条规划线以两个 fresh 子代理并行独立完成 | 串行（主会话先后独立完成两线，独立性弱于并行） |
| `--auto` / `--step-task` / `--step-group` | 执行模式（第八节） | 落档完成后询问 |
| `--engine team` | 执行引擎（第八节） | 映射文件 `engine`，再缺省 `subagent` |
| `--model <阶段>=<provider>/<模型>` | 阶段级模型覆盖（[routing.md](routing.md)） | 映射文件 `models`，再缺省继承会话模型 |

本 skill 的展开内容按**消费时机**外移到**同目录** references 文件——入口保留骨架、红线与摘要，按下表**按需读取**（读到的内容与正文同等权威）：

| 消费时机 | 读什么 |
| --- | --- |
| 阶段 1 派发规划线前 | [planning.md](planning.md) —— 并行派发模板全文、串行细节、**回执核对** |
| 派发任一子代理 / 团队成员前 | [routing.md](routing.md) —— 路由键、三档回退、白名单、图片能力、自检脚本 |
| 遇异常、边界或失败处置 | [failure-modes.md](failure-modes.md) —— 处置表主体（红线条目另见第十二节） |

**压缩后恢复速查**（红线级）：进度只认工件 + 勾选态 + 提交历史**三方对齐**（`openspec status --change <change> --json`、`tasks.md`、`git log`）；**绝不重跑已完成任务**，从最小编号未完成组继续（第七节）。

## 二、前置检查

1. **确认 OpenSpec 根**：在项目根执行 `openspec list --json`，读返回的 `root` 字段。
   - `root` 为对象 → 项目已接入，继续。
   - `"root": null` → **未接入**。此时命令退出码非 0 是「未初始化」的答案，不是 CLI 坏了，不要重试。**绝不副作用创建** `openspec/`；向用户给三选一并等待答复：①`openspec init` 初始化本项目；②指定已注册 store（`openspec store list --json` 取 id，后续命令带 `--store <id>`）；③放弃本流程，按普通对话处理。
   - 若 `status` 报错以 `Declared in` / `Invalid store declaration in` 开头并指向本项目 `openspec/config.yaml`，说明项目通过 store 接入但该 store 本机无法解析——停下展示该错误的 `message` 与 `fix`，不要当作未初始化。
2. **确认参数**：把调用参数解析为「需求原文 / continue 变更名 / 规划编排 / 执行模式 / 引擎 / 模型覆盖」，逐项记下；`continue <变更名>` 直接转第十节。
3. **记录工作目录事实**：项目根绝对路径、git 根、当前分支、`git status --porcelain` 是否干净。已有与本流程无关的脏改动 → 报告并询问如何处理，**不擅自 stash / commit / revert**。
4. **能力自检**：确认本 skill 所需的 `openspec-*` skill（`openspec-propose`、`openspec-archive-change` 等）与**阶段 1.5 问答环节所需的 `grill-me` skill** 可加载；不可加载按 [failure-modes.md](failure-modes.md) 处置顺序处理（**先核对聚合层与 skctl 登记 → 会话内执行内置 `/commands-reload` 手动重扫 → 重启容器仅作兜底**）——其中 **`grill-me` 不可加载时降级为普通按轮提问并如实告知用户**（[failure-modes.md](failure-modes.md)）。阶段 1 的两条规划线**不依赖任何外部调研 skill**：方法完全由第四节自包含定义（7 字段草案 + 独立性铁律）。
5. **路由自检**（可选，派发子代理前）：按 [routing.md](routing.md) 核对映射文件路由 ⊆ 白名单（含 `fallback`），并确认本轮若有读图任务则 `vision` 路由可用；自检不过或派发报路由错误时按 [routing.md](routing.md)**三档回退**处置，不猜、不反复重试。

## 三、模式收集

**唯一规则：一次只问该阶段需要的选项，已由参数预置的不再问，绝不自行假设。**

| 选项 | 询问时机 | 选项值 |
| --- | --- | --- |
| 规划编排 | 阶段 1 开始前（未给 `--parallel` 时） | 串行（主会话先后独立完成两线）/ 并行（两个 fresh 子代理并行独立完成） |
| 执行模式 | **落档完成、展示摘要之后** | `auto` / `step-task` / `step-group` / 暂不执行 |
| 执行引擎 | 与执行模式同时 | `subagent`（默认）/ `team` |
| 决策转达方式 | 可选，与执行模式同时（子代理上浮待决项时亦会用到） | 直接答复用户（默认）/ 授权按假设清单推进 |
| 模型覆盖 | 可选，各阶段开始前 | `--model <阶段>=<provider>/<模型>` |

用提问工具给有序选项与推荐项；把用户答复写进当前进度的简短笔记（变更名、模式、引擎、并行上限、模型覆盖），后续轮次与恢复时以笔记 + 工件为准。

## 四、阶段 1 独立双线规划（异构视角，非分工）

阶段 1 由**两条方向不同、各自完整**的规划线组成，**不是分工**：不是把一份工作切成两半各做一块，而是用两种不同视角各自把需求**完整**规划一遍。单线思考与规划必有盲区，异构双线的价值就在于让盲区在阶段 1.5 的交叉比对中互相暴露。

| 线 | 方向（异构视角） | 回答的问题 | 产物 |
| --- | --- | --- | --- |
| A 线 | 需求与价值、范围与边界 | 要解决什么、为谁解决、边界画在哪 | `/tmp/spec-flow/<change>/line-a.md` |
| B 线 | 实现与约束、反例与风险 | 怎么做、会怎么错、代价是什么 | `/tmp/spec-flow/<change>/line-b.md` |

**每条线都产出同一套字段的完整轻量规划草案**——字段固定 7 项，**不得缺项、不得合并、不得只写本方向内的那几项**（字段对齐才有可比性，阶段 1.5 才能逐字段比对）：

1. 目标与非目标
2. 范围与边界
3. 方案与取舍
4. 任务拆分草案
5. 验证思路
6. 风险与未知项
7. 假设清单

两条线的**方向不同**，但**结构与完备度要求完全一致**：B 线同样要写目标与非目标，A 线同样要写风险与未知项，只是切入视角与侧重不同。

### 独立性铁律（双线的核心价值，不得打折）

- **不得读取对方产物**：任何一条线都不读取、不检索、不引用另一条线的 `line-*.md`。
- **不得共享中间结论**：两线之间不传递任何阶段性判断；主会话也不得把一条线的结论"顺口"带进另一条线的提示。
- **不得跳过"另一条线负责的部分"**：不存在"这块归另一条线"——凡影响方案走向、与本需求相关的内容，本线一律自己写。
- **信息不足时自行查证或上浮**：能读代码、读 spec、跑只读命令查到的自己查；查不到的写进「假设清单」与「风险与未知项」；**需要用户拍板的不得自行假设**，按下方「待决问题的中转交互协议」上浮，由主会话代问用户（子代理自己不能提问，见该协议）。
- **两条线的提示除「方向」外完全等形**：同样的字段清单、同样的产物路径规则、同样的硬约束、同样的详略要求；不给任何一条线更长的篇幅预算或更多上下文。

`<change>` 取变更 slug：接续场景用既有变更名；新建场景先用需求的 kebab-case 短名，落档确定正式名后 `mv` 目录对齐（或落档后改用正式名继续写）。

### 待决问题的中转交互协议（子代理 ↔ 用户）

**平台事实**：被父代理拥有的子代理**不能直接向用户提问**——它调用提问工具会被以错误码 `DELEGATED_CALLER` 拒绝（`assertLiveRoot` 只接受存活的根会话）；`dsh-tool-ask-user` 同样写明「存活的子 agent 不能调用此工具，必须在最终结果中包含尚未解决的决定」。team 引擎的 teammate 也是被拥有的子级，受同一限制。**这是平台设计，不是故障**。但工作流要让子代理的问题**真的送到用户并拿到答复**，故约定如下中转协议——**规划线（line-a / line-b）、执行任务、复算线（panel）一律适用**：

1. **① 上浮**：子代理遇需用户拍板的决策**不得自行假设**；把每条决策写进产物「待决问题」节（**问题、选项、你的推荐、影响面**四项齐全），并在**最终回执**中把它们列为本轮 TOP 待决项，然后结束回合；**不得为等答复而阻塞、空转或轮询**（子代理没有等待通道）。
2. **② 代问**：主会话收到回执后**立即**用提问工具问用户，**不得积压到阶段末**；但**不另开提问通道**——**规划期间（阶段 1 与 1.5）的上浮项并入阶段 1.5 的设计树/前沿统一提问**（阶段 1.5 一开始即建树提问，因此不算延迟）：上浮项作为设计树节点与其余待决项一起按前沿分轮，**不单独另开一轮问答**（避免两套提问通道）；其中前置决策已定的**计入本轮**，依赖未决答案的留到其依赖落定后的轮次。每轮 **≤5 问**、每题附推荐答案并标注**推荐来源**（共识 / 复算 / 子代理建议）。执行阶段的上浮项在该批次即时代问（执行阶段没有设计树，仍走本协议）。
3. **③ 记录**：阶段 1 与 1.5 期间的问答写入 `/tmp/spec-flow/<change>/diff-matrix.md`（问题、答复、是否仍待决）；执行阶段的问答写入**当批次报告**（停留审核摘要或最终汇报）。
4. **④ 回送**（两档，按执行引擎选择——见第八节）：
   - **team 引擎**：用 `send_message` 把答复回送**同一成员**——其上下文保留，可多轮往返澄清。
   - **subagent 引擎**：把**上一轮回执摘要 + 用户答复**并入**新的子代理提示接续重派**——上下文重建，等价于续跑但**不是同一实例**，不要声称能续跑原实例。**`send_message` 无法寻址子代理**是部署实测结论：对运行中与已结束的 tool-subagent 子代理都报 `active teammate "<id>" not found`，它只寻址 `spawn_teammate` 建立的具名队友。
5. **⑤ 循环终止**：待决项清空，或用户明确授权**「按假设清单推进」**——此时**跳过代问**（②），改按子代理给出的推荐/假设继续，并在产物与阶段摘要中标注**「已授权的假设清单」**（逐条列出假设内容）。

两条禁令：

- **不得把待决项静默变成假设**：未取得答复的决策只能作为「待决项」上浮或列为已授权假设，不得当作既定事实写进工件。
- **不得让子代理为等答复而阻塞或轮询**：子代理结束回合即交还控制权，等待只发生在主会话与用户之间。

### 派发与回执细节（外移，见 planning.md）

`--parallel` 的双 fresh 子代理派发与**自包含提示模板全文**、串行模式的落盘顺序与独立性标注、**「回执核对（主会话必做）」**的核对清单与失败处置，全部见 [planning.md](planning.md)——**阶段 1 派发前先读它再动手**；两条线除「方向」外**逐字等形，缺一不可**。


## 五、差异收敛与分歧复算（阶段 1.5）

两条规划线都回执后，主会话做差异收敛——六步，一步不省；其中**第 4 步的提问环节加载并遵循 `grill-me` skill 的设计树/前沿分轮方法**（方法来自该 skill；**问答由主会话执行**——子代理自己不能提问，规划线与复算线的问题经第四节中转协议上浮后**并入同一套提问**，不再另开通道）：

1. **交叉比对**：逐字段（7 字段逐一）对齐 `line-a.md` 与 `line-b.md`，把每一条内容归入三类：
   - **共识**：两线都提出且结论一致 → 直接采信。
   - **分歧**：两线都提出但结论不同 → 交第 2、3 步裁定。
   - **单边遗漏**：只在一条线出现 → **遗漏信号**。SHALL **逐项核验**：成立则纳入落档，不成立则写明理由后丢弃；**绝不因"只有一条线提出"而丢弃**。
2. **自行裁定**：能从代码、规范或只读命令查证的分歧，**主会话自己查证**（必要时派只读子代理），记录裁定依据（查了什么、结论是什么）；**不得转为提问**。
3. **分歧复算（第三条线）**：仅对「影响方案走向**且**无法从环境查证」的分歧，派第三条 **fresh** 子代理（`panel` 路由）复算。
   - 复算子代理**不以任何既有草案为输入**：只给**分歧点陈述 + 需求原文**，要求它给出**独立判断 + 理由 + 反例**。
   - **三线对照**：两线一致或 2:1 → 形成结论、依据与置信说明；三条互不相同 → 升级为**用户决策项**。
   - **默认每次流程最多复算 3 个分歧点**（超出时按影响面排序取前 3），其余升级为决策项。
4. **按 `grill-me` 方法问决策项**（加载并遵循 `grill-me` skill；本 workflow 只把「怎么问」交给它，其余步骤不变）：
   - **映射为设计树**：把全部待决项——规划线「待决问题」节上浮的、复算后仍存的分歧、单边项核验后仍待定的取舍——映射为一棵**设计树**：**节点即决策，边即依赖**（某决策的答案是否会改变另一决策的前提 / 选项）。
   - **只问前沿**：**前沿** = 前置决策已定、现在就能问而不必猜未听到答案的那批问题。**仅前沿问题进本轮**；**依赖未决答案的问题留到后续轮次，不得同轮抛出**。
   - **每轮 ≤5 问**：前沿更大时先问**承重最大**的（挂靠决策最多的那些），其余自然成为下一轮前沿；每题**编号**并**附推荐答案**，措辞使「是 / 同意」即等于接受该推荐答案，同时标注推荐来源（共识 / 复算 / 子代理建议）。
   - **事实自行查证**：需要环境事实（文件、代码、规范、命令输出）时自己读代码、读规范、跑只读命令，必要时派只读子代理去查——**不向用户索取可查证的事实**（与第 2 步同一原则）；查证未回期间只有其下游问题等待，**其余前沿照问**（事实未定即前置未定）。
   - **答完重算前沿**：用户答完一轮，前置随之落定，**重新计算前沿**再给下一轮。
   - **收敛结束条件**：**前沿为空**，或用户**明确确认「已达成共识 / 可以落档」**；用户确认前不得据此行动（尤其不得落档）。
   - **答复回送**：需要子代理据此继续的答复，按引擎**回送同一成员或接续重派**（第四节中转协议）；上浮项只并入本设计树，不另开问答通道。
   - **不因此改变的部分**：本 workflow 的**三分类（共识 / 分歧 / 单边遗漏）、自行裁定、第三线复算与 `diff-matrix.md` 留痕一概不变**——`grill-me` 只接管「怎么问」，待决项的**来源、裁定与复算逻辑**仍按第 1–3 步执行。
5. **记录**：单边项核验结果、裁定依据、复算结论与**设计树/前沿分轮的问答**（问题、答复、是否仍待决）**全部写入** `/tmp/spec-flow/<change>/diff-matrix.md`（三分类矩阵 + 设计树与前沿分轮记录 + 依据 + 结论），它是阶段 2 落档的输入之一。
6. **收敛结束**：**前沿为空**（设计树每条分支都走到、没有被静默假设的项），或用户在**明确确认「已达成共识 / 够了，可以落档」**后结束；确认之前不得据提问结果行动（不得落档）。仍未答的项**不得静默假设**——写进落档 design 的「未决/后续」并在落档摘要里列出。

用提问工具（单选/多选 + 推荐项）**按前沿分轮**问；**只问决策，不问事实**。

## 六、落档（阶段 2）

加载 `openspec-propose` skill，按其规程生成工件；输入 = 需求原文 + `/tmp/spec-flow/<change>/` 的 `line-a.md` + `line-b.md` + `diff-matrix.md`（缺 `diff-matrix.md` 说明阶段 1.5 未做完，先补做再落档）。

1. **生成四件套**：`proposal.md`、`specs/<capability>/spec.md`（delta，保持既有 capability 路径）、`design.md`、`tasks.md`。
2. **`tasks.md` 必须满足执行批次契约**（硬约束，后续执行直接依赖）：
   - 以 `## N. 组名` 编号分组表达**执行批次**；`N` 递增即执行顺序，**组间严格串行**。
   - **组内任务互不依赖、可并行**：不得含互为前置、或写同一文件/同一目录的多个任务；有此情况必须拆到不同组。
   - 每任务一行 `- [ ] N.M <一句可执行描述>；验证：<验证句>`。
   - **验证句**必须是第三方可核对的（具体命令、文件路径+断言、可观察输出），禁止「已实现」「工作正常」这类空话。例：`验证：python3 -c "import yaml;d=yaml.safe_load(open('x.yaml'));assert 'models' in d"` 退出码 0；或 `验证：grep -n 'spec-workflow' agent/skills/README.md 命中且表格行存在`。
   - 单组任务数以映射文件 `parallelism`（默认 3）为上限，超出则拆组。
3. **分歧点提问**：工件之间存在取舍、design 有多种方案、需求有歧义时，一次问清；不自行拍板。
4. **校验**：`openspec validate <change> --strict`，必须退出码 0 且无 error/warning；不通过则修工件重跑，**不得带病进入执行**。
5. **落档即停（规划边界）**：本阶段只产出规划工件，**不写项目代码、不在同一轮继续执行**。
6. **展示摘要**：变更名、四件套路径、任务组数与条数、每组并行度、验证句样例、风险与未决项（含阶段 1.5 差异收敛中未答的决策项）。
7. **问执行模式**（未预置时）：`auto` / `step-task` / `step-group` / **暂不执行**；并确认引擎（参数 `--engine` > 映射文件 `engine` > 默认 `subagent`）。
8. **落档工件单独提交一次**：只 `git add` 该变更目录（`openspec/changes/<change>`，含新建的 spec delta），提交信息 `docs(openspec): 落档 <change>`；目标仓库既有中文惯例（如 `docs(spec-workflow): 落档 <change> 规划工件`）时从惯例。提交后再进入第七节。
9. 用户选「暂不执行」→ 就此结束，告知用 `/spec-flow continue <change>` 随时接续。

## 七、衔接与恢复协议

**衔接（落档提交后、执行前）**：

1. 确认执行模式与引擎（第六节第 7 步；接续场景见第十节需重选一次）。
2. 提示用户（原话模板）：**「如需切换主会话模型请现在切换，也可 /compact 压缩上下文，然后说继续。」** 本 skill 无法修改主会话模型，只能在阶段边界提示；被打断的会话按恢复协议重建进度即可，不丢工作。

**恢复协议（任何时刻生效：新轮次、`/compact` 之后、会话重启之后、用户说「继续」）**：

1. 先重建进度，再动手：`openspec status --change <change> --json`（注意：**该 CLI 版本的 `status` 不接受位置参数**，`openspec status <change>` 会报 `too many arguments`，必须用 `--change`；裸 `openspec status --json` 会报 `Missing required option --change`，该版本用 `openspec status --all --json` 或 `openspec list --json` 兜底）读工件完成度。
2. 读 `openspec/changes/<change>/tasks.md` 勾选态（`- [x]` = 完成）与 `git log --oneline` 中已完成批次的提交。
3. 三方对齐：**工件 + 勾选态 + 提交历史**。只认勾选且能与改动/提交对上的任务；勾选但无验证证据或提交对不上 → 回退为未完成并报告。
4. **绝不重跑已完成任务**；从「最小编号的未完成组」继续，已完成组不重开。
5. 恢复后先输出一行进度摘要（`change / 已完成 N/M 任务 / 当前组 / 引擎 / 模式 / 下一步`），再继续执行。
6. 恢复所需上下文一律从工件现读（specs、design、tasks），**不依赖对话记忆**；这正是上下文压缩或重启后可无损恢复的原因。

## 八、执行双引擎与三模式（阶段 3）

批次循环骨架：

```
while 存在未勾选任务:
    组 = 编号最小的未完成组
    if 引擎 == subagent: 组内每任务派一个 fresh 子代理（同一条消息并发，上限 parallelism）
    else:                组内任务发布到共享任务板，spawn ≤ 组内任务数的 implementer 认领
    主会话逐任务核对（验证句 + 读改动 + git diff）→ 通过才勾选 tasks.md
    按执行模式决定：停留审核 / 提交 / 直接进入下一组
```

**subagent 引擎（默认）**：

- 每个任务一个 **fresh** 子代理（不要用继承上下文的 fork；只有 fresh 支持模型选择）。
- 提示自包含（缺一不可）：项目根绝对路径、**任务原文（含编号）**、相关 spec/design 摘录、验收标准=**验证句原文**、写范围（允许改的文件/目录）、禁止事项（不 `git add`/`git commit`、不改 `tasks.md` 勾选、不改写范围外文件、不跑破坏性或不可逆命令）。
- 组内并发派发、**组间串行**；并行上限取映射文件 `parallelism`（默认 3）。
- 回执格式要求：改动文件清单、验证命令与输出摘要、偏差与未完成项、**待决问题（TOP 待决项）**。按 [routing.md](routing.md) 给任务子代理应用 `apply` 路由（任务需读图时改用 `vision` 路由）。
- **待决问题中转**（第四节协议）：子代理遇需用户拍板的决策不得自行假设，在产物与回执中上浮 → 主会话**立即代问用户**（≤5 问/轮）→ 把**上一轮回执摘要 + 用户答复**并入新提示**接续重派**（上下文重建，非同一实例）。**这正是让 subagent 事实上能与用户交互的机制**：子代理自身不能提问（`DELEGATED_CALLER`），问题与答复经主会话中转。
- 核对不通过：auto 模式 → 派发修复子代理（附失败输出）后重新核对；step 模式 → 向用户呈现问题与证据等裁决（见 [failure-modes.md](failure-modes.md)「审核被拒」）。

**team 引擎（可选，实验性 Agent Teams）**：

- 仅 `--engine team` 或映射文件显式启用时使用；否则不启用。成员创建失败或不可用时按 design「风险与回退」**降级为 subagent** 完成该任务。
- 主会话作为 Lead：用任务板工具（挂载 Agent Teams 时 Lead 可见 `team_task_create` / `team_task_list` / `team_task_get` / `team_task_update`，以当前会话实际挂载的工具名为准）把组内每个任务发布到**共享任务板**，卡片含任务原文、**验证句**、写范围、产出要求。
- `spawn_teammate` 创建具名 implementer，**成员数 ≤ 组内任务数**（并受 `parallelism` 封顶），成员按卡片 `owner` 认领执行；用 `list_agents` / `wait_agent` 观察。
- **审核反馈走消息**：`send_message` 把修改要求发给负责该任务的成员，由其在同一上下文内修复（保留其上下文，不重派新成员）。
- **待决问题中转**（第四节协议）：成员上浮的待决项由 Lead **立即代问用户**，再用 `send_message` 把答复**回送同一成员**（上下文保留、可多轮往返澄清）——与「审核反馈走消息」同一条通道。**这是让被拥有的 teammate 事实上能与用户交互的机制**（成员自身同样不能直接提问）。
- 成员卡死或创建失败：`interrupt_agent` 中断后重建；无法恢复则降级 subagent 完成该任务。
- 该引擎**忽略 `apply` 路由键，阶段级模型路由整体不适用**（teammate 创建工具无模型参数，fork teammate 锁定 Lead 模型）。

**两引擎共同纪律**：主会话必须自己按**验证句 + diff** 核对（跑验证句里的命令或检查点、读回改动文件、`git diff --stat` 与必要处 `git diff`），**核对通过才把 `- [ ]` 改成 `- [x]`**；不得仅凭子代理口头汇报勾选。

**三种执行模式与提交节奏**：

| 模式 | 停留点 | 提交时机 | 提交信息示例 |
| --- | --- | --- | --- |
| `auto` | 不停留（除下方硬停条件） | 全部任务完成后提交一次 | `feat(<scope>): 完成 <change> 实现` |
| `step-task` | **每个任务**核对后停留审核 | 每批次审核通过后提交一次 | `feat(<scope>): 批次 N <组名>` |
| `step-group` | **每个批次（组）**核对后停留审核 | 每批次审核通过后提交一次 | 同上 |

- 停留时展示变更摘要：批次号、任务号、改动文件、验证输出摘要、diff stat，然后等用户确认（继续 / 修改 / 停止）。
- 提交纪律：只 `git add` 本批次涉及的文件（含 `tasks.md` 勾选）；不提交密钥、构建产物、日志、临时文件；批次提交信息**含批次号**。
- `auto` 模式的**硬停条件**（必须停下来问用户，不得自行推进）：①不可逆操作（删除/覆盖/force push/数据迁移/发布上线）；②安全敏感（凭据、密钥、权限、生产配置）；③工作区外副作用（改宿主文件、其他仓库、重启容器或服务）；④计划彻底失效（实现与 design/spec 前提矛盾）。除此之外 auto 不在任务之间询问「是否继续」。
- 任务失败：**重试一次**（同一提示 + 上次失败输出摘要）；仍失败则**暂停本批次并报告**（任务号、错误摘要、已完成/未完成清单、建议），不中断整个流程、不擅自动其他批次。

## 九、验证与归档（阶段 4）

1. **先读目标项目声明的验证方式**：项目根 `AGENTS.md` / `CLAUDE.md`（其次 `README`、`package.json` scripts、`Makefile`、CI 配置）。项目声明优先于通用猜测。
2. **执行验证**：可派 **fresh** 子代理执行（按 [routing.md](routing.md) 应用 `verify` 路由），提示自包含（项目路径、要跑的命令、期望结果、只读约束），回传命令与输出摘要；失败必须回传关键错误段。聚合多个命令时逐条记录退出码。
3. **验证不通过 → 不归档**。报告失败证据（命令、输出、涉及任务），问用户：修复（回到阶段 3 派修复任务）或明确跳过（记录为已知缺口，需用户显式批准后才继续）。
4. **通过后归档**：确认 `tasks.md` 全部勾选（有未勾选项不得归档），加载 `openspec-archive-change` skill 执行归档并同步主规格。
5. **归档单独提交一次**（`docs(openspec): 归档 <change>`），不与批次改动混提。归档报错 → 贴错误原文并停，不手工搬移目录。
6. **最终汇报四要素**：①变更名与工件路径；②验证证据（命令 + 结果摘要）；③归档位置（`openspec/changes/archive/...` 与同步后的主规格）；④后续宿主操作清单（需要用户在容器外做的事，如 skctl 登记、推送 `git push`、以及命令仍不可见时的 `docker compose restart dsh` 兜底——本流程不代劳）。

## 十、接续流程

触发：`/spec-flow continue <变更名>`，或用户要求接续/继续某个未完成变更。

1. 先跑**恢复协议**（第七节）重建进度。
2. 校验变更存在且未归档：`openspec list --json`（活跃变更）；已归档 → 报告并结束。`tasks.md` 为空或不存在 → 说明尚未落档，问用户是否回到阶段 1/2。
3. **跳过已完成的规划与落档**（`/tmp/spec-flow/` 材料可能已随重启丢失，不需要它即可续跑）；仅当用户明确要求「重跑规划 / 重做落档」时才重跑对应阶段，且重跑前说明将覆盖哪些工件（已提交的工件改动同样走第六节第 8 步单独提交）。
4. **执行前重新确认一次执行模式与引擎**（不沿用上次假设），再按第八节从最小编号未完成组续跑。
5. 若上次停在审核点（step 模式）或失败点（重试仍失败），先呈现上次的裁决/失败证据，再继续。

## 十一、模型路由

映射文件 **`/home/xuqinqin/develop/dotfiles/dsh/spec-workflow.yaml`**（**绝对**路径；容器内 `~` = `/home/docker`）：键 `lineA` / `lineB` / `panel` / `apply` / `verify` / `vision` → 阶段 1 A/B 线、1.5 复算线、阶段 3 执行（**仅 `subagent` 引擎**；team 忽略本键）、阶段 4 验证、**读图覆盖（能力键）**；值 `{ provider, model }`，可选 `fallback`。**优先级：`--model` > 映射文件 > 继承会话模型。**

- **三档回退（顺序固定，不反复重试同一路由）**：① 有 `fallback` → 备用路由**重派一次**；② 无或备用也失败 → **回退继承会话模型**一次；③ 仍失败 → 报告该路由与错误原文并暂停。

## 十二、边界与失败

**红线级条目**（违反即致不可逆、失控或静默假设）；其余异常、边界与失败处置见 [failure-modes.md](failure-modes.md)，**遇异常先读它**：

| 情形 | 处置 |
| --- | --- |
| 无 openspec 根（`root: null`） | 问 init / store / 放弃，**绝不副作用创建** `openspec/`（第二节） |
| 子代理需要用户决策 / 直接提问被拒（`DELEGATED_CALLER`） | 走第四节「待决问题的中转交互协议」：上浮 → 主会话**立即代问用户** → team 用 `send_message` 回送**同一成员**、subagent 接续重派。**`DELEGATED_CALLER` 是平台设计，不是故障**——不判定工具损坏、不重试直接提问 |
| 计划彻底失效（工件与实现矛盾） | `auto` 硬停条件之一（四条件全文见第八节）：停下让用户决定重做落档（改工件）或终止 |


**绝不做**：不自行 `openspec init`；不提交未过审或未验证的内容；不动目标项目的 CI、密钥、生产配置；不替用户切换主会话模型；不在 `auto` 之外的模式下跳过审核点；不把子代理上浮的待决项**静默变成假设**；不把 `/tmp/spec-flow/` 的临时材料当成进度依据（权威进度永远是工件 + 勾选态 + 提交历史）。

## 附：阶段 1 双线派发细节（自 SKILL.md §四 外移）

### 并行模式（`--parallel`）

在**同一条消息**内派发两个 **fresh** 子代理（`run_in_background: true`），等待两者都回传。提示必须**自包含**，模板如下（两条线除「方向」外逐字等形，缺一不可）：

```
项目根（绝对路径）：<project root>
需求原文：<用户需求，逐字>
你的规划方向：<A：需求与价值、范围与边界——要解决什么、为谁解决、边界在哪
              | B：实现与约束、反例与风险——怎么做、会怎么错、代价是什么>
你的产物路径：/tmp/spec-flow/<change>/line-a.md   （B 线为 line-b.md）
产出要求：一份**完整的轻量规划草案**，下列 7 个字段**全部**写到、字段名照抄，不得缺项、不得合并、不得只写你方向内的那几项：
  1) 目标与非目标  2) 范围与边界  3) 方案与取舍  4) 任务拆分草案
  5) 验证思路      6) 风险与未知项  7) 假设清单
另立「待决问题」节（在 7 字段之外）：每条含 问题 / 选项 / 你的推荐 / 影响面；无待决项时写「无」。
事实自己查（读代码、读 spec、跑只读命令）；查不到的写进「假设清单」与「风险与未知项」。
硬约束：
- 只允许写你自己的那一份产物文件；不得写项目文件、不得改 openspec/、不得 git add/commit。
- 不与用户直接交互：**你看不到用户、也不能提问**——被拥有的子代理调用提问工具会被以错误码 `DELEGATED_CALLER` 拒绝。需要用户拍板的决策**不要自行假设**：写进产物「待决问题」节（每条含：**问题、选项、你的推荐、影响面**），并在**最终回执**中把它们列为本轮 TOP 待决项后结束回合——**不要为等答复而空转、阻塞或轮询**；主会话会代问用户并按引擎把答复回送（见「待决问题的中转交互协议」）。
- 不得读取、引用另一条规划线的产物，也不得等待它。
```

### 串行模式（默认）

用户未给 `--parallel` 时：主会话**先独立完成 A 线并落盘** `line-a.md`，再**在不回看 `line-a.md` 结论的前提下**独立完成 B 线并落盘。两条线仍各自写满 7 字段，不得因"A 已经想过"而略写 B。

阶段摘要**必须标注**：**「串行独立性弱于并行」**——同一会话先后完成两条线，先入为主的结论难以真正隔离；**仅建议需求较小时使用**。需求越复杂越应当用 `--parallel`：**独立性是双线的核心价值**。

**回执核对（主会话必做）**：两份产物**都存在且非空** → 各读一遍，核对 7 字段是否齐备、能否明显看出两条线**方向上的差异**（两份草案结论雷同或字段残缺 → 独立性不成立，按失败处理）→ 输出 3–8 行阶段摘要（两线各自的关键判断、已可见的分歧点、单边项信号）作为阶段边界汇报；两线上浮的**待决问题按中转协议②并入阶段 1.5 的设计树/前沿统一提问**（不另开问答通道，不积压到阶段末）；某线**缺失 / 为空 / 答非所问** → 视为该线失败：**重派一次**，仍失败则**如实报告**，由**用户决定**是否降级为串行模式重做该线（不得静默降级）。派发时按第十一节给 A / B 线分别应用 `lineA` / `lineB` 路由（某线需要读图时改用 `vision` 路由）。

## 附：前置检查展开（自 SKILL.md §二 外移；仅展开 ①④⑤，编号与入口 §二 一一对应）

**②参数** 与 **③工作目录事实** 的正文留在入口 §二，此处不重复（防双源漂移）。

**①OpenSpec 根**：在项目根执行 `openspec list --json`，读返回的 `root` 字段。
   - `root` 为对象 → 项目已接入，继续。
   - `"root": null` → **未接入**。此时命令退出码非 0 是「未初始化」的答案，不是 CLI 坏了，不要重试。**绝不副作用创建** `openspec/`；向用户给三选一并等待答复：①`openspec init` 初始化本项目；②指定已注册 store（`openspec store list --json` 取 id，后续命令带 `--store <id>`）；③放弃本流程，按普通对话处理。
   - 若 `status` 报错以 `Declared in` / `Invalid store declaration in` 开头并指向本项目 `openspec/config.yaml`，说明项目通过 store 接入但该 store 本机无法解析——停下展示该错误的 `message` 与 `fix`，不要当作未初始化。

**④能力自检**：确认本 skill 所需的 `openspec-*` skill（`openspec-propose`、`openspec-archive-change` 等）与**阶段 1.5 问答环节所需的 `grill-me` skill** 可加载；不可加载按 [failure-modes.md](failure-modes.md) 处置顺序处理（**先核对聚合层与 skctl 登记 → 会话内执行内置 `/commands-reload` 手动重扫 → 重启容器仅作兜底**）——其中 **`grill-me` 不可加载时降级为普通按轮提问并如实告知用户**（[failure-modes.md](failure-modes.md)）。阶段 1 的两条规划线**不依赖任何外部调研 skill**：方法完全由第四节自包含定义（7 字段草案 + 独立性铁律）。
**⑤路由自检**（可选，派发子代理前）：按 [routing.md](routing.md) 核对映射文件路由 ⊆ 白名单（含 `fallback`），并确认本轮若有读图任务则 `vision` 路由可用；自检不过或派发报路由错误时按 [routing.md](routing.md)**三档回退**处置，不猜、不反复重试。


## 附：代码设计环节（阶段 1.7）

**消费时机**：阶段 1.5 收敛结束之后、阶段 2 落档之前。**恒派 fresh 子代理**（按 [routing.md](routing.md) 应用 `design` 路由，默认与规划三线同级强模型），**不随阶段 1 的编排模式变化**（串行下主会话自做=自查自纠）。提示必须**自包含**，模板如下：

```
你的角色：**代码设计线（阶段 1.7）**——产出**代码级蓝图**（触达哪些文件、怎么改、接口与数据形状、为什么这么定）；双线=需求级轻重与风险，设计线=代码级蓝图，**不要把双线结论复读一遍**
项目根（绝对路径）：<project root>
需求原文：<用户需求，逐字>
输入材料（逐字读全）：需求原文 + /tmp/spec-flow/<change>/line-a.md + line-b.md + diff-matrix.md
你的产物路径：/tmp/spec-flow/<change>/code-design.md
产出要求（深度契约，内容六字段，字段名照抄、不得缺项、不得合并）：
  ① 触达面清单：逐文件路径 + 改动意图 + 关键改动点
  ② 证据锚：每个触达模块 ≥1 条 file:line 代码事实；新建文件标「新建」
  ③ 接口与数据形状：函数签名 / 类型 / 配置键
  ④ 决策记录：每个决策附**被否方案与理由**，≥1 条反例
  ⑤ 逐任务组实现要点：与 tasks 的任务分组一一对齐
  ⑥ 设计假设与未决项
行为约束（二条，恒成立）：
  - 验证映射落**具体命令或断言**，禁止「已实现」「工作正常」这类空话
  - **不推翻** diff-matrix.md 的收敛结论；发现矛盾**上浮待决，不重开收敛**
另立「待决问题」节（在六字段之外）：每条含 问题 / 选项 / 你的推荐 / 影响面；无待决项时写「无」。
硬约束：只允许写你自己的那一份产物；不得写项目文件、不得改 openspec/；不得读取、引用或等待其他子代理。
```

**回执核对清单**（主会话逐条做，顺序固定）：①产物**存在且非空** → ②六字段**齐备** → ③触达面**逐路径点名**（每条含路径与关键改动点，不空泛）→ ④逐组要点**覆盖全部任务组** → ⑤待决项**上浮**（并入落档提问）。任一条不过 → **重派一次**；仍失败按 [failure-modes.md](failure-modes.md) 同构处置并**如实报告**，不得静默降级。

**上浮接线**：阶段 1.7 的待决问题**并入「落档细节」第 3 步「分歧点提问」**一次问清——不新开通道、不积压到落档之后。

**三档分降**（主会话在派发前判定，档位记入阶段摘要）：
- **L2 全深度**（默认）：六字段与二行为约束全部执行。
- **L1**（触达面 ≤2 文件**且**无新接口）：字段 ③④⑤ 与验证映射允许**单行简述**；①⑥ 与二行为约束**恒成立**。
- **L0**（trivial：单文件 + 无接口变更 + 无逻辑分支变化）：**豁免 fresh 派遣**，主会话 **inline 一行断言**落档；**产物 schema 恒在**（`code-design.md` 必须存在，内容即该一行断言）。


## 附：落档细节（自 SKILL.md §六 外移）

加载 `openspec-propose` skill，按其规程生成工件；输入 = 需求原文 + `/tmp/spec-flow/<change>/` 的 `line-a.md` + `line-b.md` + `diff-matrix.md` + `code-design.md`（**第 5 材料**，阶段 1.7 产物；缺 `diff-matrix.md` 说明阶段 1.5 未做完、缺 `code-design.md` 说明阶段 1.7 未做完——先补做再落档）。

1. **生成四件套**：`proposal.md`、`specs/<capability>/spec.md`（delta，保持既有 capability 路径）、`design.md`、`tasks.md`。`design.md` **逐断言承载 `code-design.md` 的深度契约**（①触达面 ②证据锚 ③接口与数据形状 ④决策 ⑤逐组要点 ⑥假设与未决项），落档时**逐条核对**通过后再继续。
2. **`tasks.md` 必须满足执行批次契约**（硬约束，后续执行直接依赖）：
   - 以 `## N. 组名` 编号分组表达**执行批次**；`N` 递增即执行顺序，**组间严格串行**。
   - **组内任务互不依赖、可并行**：不得含互为前置、或写同一文件/同一目录的多个任务；有此情况必须拆到不同组。
   - 每任务一行 `- [ ] N.M <一句可执行描述>；验证：<验证句>`；描述须**引用该任务触达文件在 `code-design.md` 触达面清单中的条目编号**（硬契约，「组内不写同一文件」据此机械化核对）。
   - **验证句**必须是第三方可核对的（具体命令、文件路径+断言、可观察输出），禁止「已实现」「工作正常」这类空话。例：`验证：python3 -c "import yaml;d=yaml.safe_load(open('x.yaml'));assert 'models' in d"` 退出码 0；或 `验证：grep -n 'spec-workflow' agent/skills/README.md 命中且表格行存在`。
   - 单组任务数以映射文件 `parallelism`（默认 3）为上限，超出则拆组。
3. **分歧点提问**：工件之间存在取舍、design 有多种方案、需求有歧义时，一次问清；不自行拍板。**阶段 1.7 设计线上浮的待决项并入此处**（见「附：代码设计环节（阶段 1.7）」的上浮接线），不新开通道。
4. **校验**：`openspec validate <change> --strict`，必须退出码 0 且无 error/warning；不通过则修工件重跑，**不得带病进入执行**。
5. **落档即停（规划边界）**：本阶段只产出规划工件，**不写项目代码、不在同一轮继续执行**。
6. **展示摘要**：变更名、四件套路径、任务组数与条数、每组并行度、验证句样例、风险与未决项（含阶段 1.5 差异收敛中未答的决策项）。
7. **问执行模式**（未预置时）：`auto` / `step-task` / `step-group` / **暂不执行**；并确认引擎（参数 `--engine` > 映射文件 `engine` > 默认 `subagent`）。
8. **落档工件单独提交一次**：只 `git add` 该变更目录（`openspec/changes/<change>`，含新建的 spec delta），提交信息 `docs(openspec): 落档 <change>`；目标仓库既有中文惯例（如 `docs(spec-workflow): 落档 <change> 规划工件`）时从惯例。提交后再进入第七节。
9. 用户选「暂不执行」→ 就此结束，告知用 `/spec-flow continue <change>` 随时接续。


## 附：接续细节（自 SKILL.md §十 外移）

触发：`/spec-flow continue <变更名>`，或用户要求接续/继续某个未完成变更。

1. 先跑**恢复协议**（第七节）重建进度。
2. 校验变更存在且未归档：`openspec list --json`（活跃变更）；已归档 → 报告并结束。`tasks.md` 为空或不存在 → 说明尚未落档，问用户是否回到阶段 1/2。
3. **跳过已完成的规划与落档**（`/tmp/spec-flow/` 材料可能已随重启丢失，不需要它即可续跑）；仅当用户明确要求「重跑规划 / 重做落档」时才重跑对应阶段，且重跑前说明将覆盖哪些工件（已提交的工件改动同样走第六节第 8 步单独提交）。
4. **执行前重新确认一次执行模式与引擎**（不沿用上次假设），再按第八节从最小编号未完成组续跑。
5. 若上次停在审核点（step 模式）或失败点（重试仍失败），先呈现上次的裁决/失败证据，再继续。

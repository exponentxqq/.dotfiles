> 本文件为 SKILL.md 第六节（双引擎、三模式与提交纪律、硬停条件）与第七节（验证与归档派发要点）的外移正文；回入口引用写「SKILL.md 第 6 节」「第 7 节」。

**subagent 引擎（默认）**：

- 每个任务一个 **fresh** 子代理（不要用继承上下文的 fork；只有 fresh 支持模型选择）。
- 提示自包含（缺一不可）：**项目根绝对路径**（隔离执行时 = worktree 路径，见 [worktree.md](worktree.md)）、**任务原文（含编号）**、**design.md 中该任务所属组的实现要点逐字引用**（不得转述）、验收标准=**验证句原文**、写范围（允许改的文件/目录，须含该任务触达面条目所列文件）、禁止事项（不 `git add`/`git commit`、不改 `tasks.md` 勾选、不改写范围外文件、不跑破坏性或不可逆命令）、**栈对应 writer skill 加载指令**——**从落档 `design.md` 决策记录读取**栈识别结论后点名 skill 名（豁免时注明依据；**记录无从取得则重识别一次**并更新落档记录——加载失败按待决问题上浮，不静默跳过）。
- 组内并发派发、**组间串行**；并行上限取映射文件 `parallelism`（默认 3）。
- 回执格式要求：改动文件清单、验证命令与输出摘要、偏差与未完成项、**待决问题（TOP 待决项）**。按 [routing.md](routing.md) 给任务子代理应用 `apply` 路由（任务需读图时改用 `vision` 路由）。
- **待决问题中转**（第六节协议）：子代理遇需用户拍板的决策不得自行假设，在产物与回执中上浮 → 主会话**立即代问用户**（≤5 问/轮）→ 把**上一轮回执摘要 + 用户答复**并入新提示**接续重派**（上下文重建，非同一实例）。**这正是让 subagent 事实上能与用户交互的机制**：子代理自身不能提问（`DELEGATED_CALLER`），问题与答复经主会话中转。
- 核对不通过：auto 模式 → 派发修复子代理（附失败输出）后重新核对；step 模式 → 向用户呈现问题与证据等裁决（见 [failure-modes.md](failure-modes.md)「审核被拒」）。

**team 引擎（可选，实验性 Agent Teams）**：

- 仅 `--engine team` 或映射文件显式启用时使用；否则不启用。成员创建失败或不可用时按 design「风险与回退」**降级为 subagent** 完成该任务；**成员上限达限（`Team member limit 8 reached`）同此处置**并在留痕中记录。
- 主会话作为 Lead：用任务板工具（挂载 Agent Teams 时 Lead 可见 `team_task_create` / `team_task_list` / `team_task_get` / `team_task_update`，以当前会话实际挂载的工具名为准）把组内每个任务发布到**共享任务板**，卡片含任务原文、**验证句**、写范围、产出要求，以及**与 subagent 引擎同款的栈对应 writer skill 加载指令**（从落档 design.md 决策记录点名 skill 名）。
- `spawn_teammate` 创建具名 implementer，**成员数 ≤ 组内任务数**（并受 `parallelism` 封顶），成员按卡片 `owner` 认领执行；用 `list_agents` / `wait_agent` 观察。
- **审核反馈走消息**：`send_message` 把修改要求发给负责该任务的成员，由其在同一上下文内修复（保留其上下文，不重派新成员）。
- **待决问题中转**（第六节协议）：成员上浮的待决项由 Lead **立即代问用户**，再用 `send_message` 把答复**回送同一成员**（上下文保留、可多轮往返澄清）——与「审核反馈走消息」同一条通道。**这是让被拥有的 teammate 事实上能与用户交互的机制**（成员自身同样不能直接提问）。
- 成员卡死或创建失败：`interrupt_agent` 中断后重建；无法恢复则降级 subagent 完成该任务。
- 该引擎**忽略 `apply` 路由键，阶段级模型路由整体不适用**（teammate 创建工具无模型参数，fork teammate 锁定 Lead 模型）。

**引擎可批次间切换**：任一批次开始前可按用户指示切换引擎（含 team↔subagent），自该批次起生效；**切换与原因写入留痕**（执行期留痕，见下）。

## 附：三模式与提交纪律、硬停条件（自 SKILL.md §六 外移）

**三种执行模式与提交节奏（审核点与提交点分离——任何模式，完成后都不自动提交）**：

| 模式 | 停留点 | 提交时机 | 提交信息示例 |
| --- | --- | --- | --- |
| `auto` | 批次间不打断；**全部批次完成后停留呈证** | **用户审核确认后**提交一次 | `feat(<scope>): 完成 <change> 实现` |
| `step-task` | **每个任务**核对后停留审核 | **用户审核确认后**该批次提交一次 | `feat(<scope>): 批次 N <组名>` |
| `step-group` | **每个批次（组）**核对后停留审核 | 同上 | 同上 |

- **停留时展示证据**：批次号、任务号、改动文件、验证输出摘要、diff stat，然后**等用户确认**（继续 / 修改 / 停止）。**主会话核对通过不等同于审核通过**：核对通过才勾选 `tasks.md`，**提交一律在用户审核确认之后**（用户明确豁免审核时才可跳过等待，豁免指令须留痕）。
- **提交纪律**：只 `git add` 本批次涉及的文件（含 `tasks.md` 勾选）；不提交密钥、构建产物、日志、临时文件；批次提交信息**含批次号**。
- **多仓分立提交**：代码、工件、生成物各归其仓——嵌套独立子仓（如根仓承载 openspec 工件、子仓承载代码）与工作区外独立仓（用户明示参与后）同循此则：**N 仓各自形成完整提交、不跨仓混提**；隔离执行时代码仓的检出即 worktree（`feature/<change>` 分支）——代码提交仍在该 worktree 内做、工件提交仍在根仓主工作区，布局与装配见 [worktree.md](worktree.md)。
- **外部仓外溢口径**：执行期需求波及工作区外独立仓 = 规划外 scope 变化 → 停下回用户（呈证点呈报或按硬停条件③）；用户明示后改动随该仓提交、R<n> 留痕注明外溢。
- **真实凭据纪律**：验证/冒烟需要的真实密钥**只经命令行参数或环境变量传入进程**，绝不写入任何入库文件、工件、日志或提交信息；凭据缺失时以明确报错失败（如提示缺少参数），**不静默跳过、不伪造结果**。
- **中途恢复（`auto` 尤甚）**：勾选任务的改动**尚在工作区、未提交属预期**（收尾经用户确认才提交）；**先对现存 diff 跑该任务验证句**——通过即**保持勾选、不重派子代理**，未通过才回退该勾选并报告。
- `auto` 模式的**硬停条件**（必须停下来问用户，不得自行推进）：①不可逆操作（删除/覆盖/force push/数据迁移/发布上线）；②安全敏感（凭据、密钥、权限、生产配置）；③工作区外副作用（改宿主文件、其他仓库、重启容器或服务）；④计划彻底失效（实现与 design/spec 前提矛盾）。除此之外 auto 不在批次之间询问「是否继续」。
- 任务失败：**重试一次**（同一提示 + 上次失败输出摘要）；仍失败则**暂停本批次并报告**（任务号、错误摘要、已完成/未完成清单、建议），不中断整个流程、不擅自动其他批次。

## 附：执行期留痕与工件维护（组收尾必做）

- **勾选核对**：本组任务全部 `- [x]` 才进工件维护与呈证——发现未勾先补跑该任务验证句核对再勾；勾选与工件维护、提交同为组收尾必做。
- **`code-design.md` 组段终形态化**：每组核对完成后，把该任务组对应的组段更新为**终形态**——含实测事实（框架 API 行为、环境约束）、被否方案与理由、验收数据；后续组与接续恢复以工件为准。**维护目标是变更目录内的落档副本（`openspec/changes/<change>/code-design.md`，spec-plan 落档时复制入库），更新随批次提交入库；`/tmp` 侧原件不再维护**。**前提——落档副本在变更目录**：缺失按 SKILL.md 第五节恢复协议补复制或问用户，**不得以 /tmp 原件替代维护**。
- **运行规则编号留痕**：执行中新证实的项目级运行规则（构建工具怪癖、目录约定、验收口径等）以 **R<n> 编号条目**追加到 `tasks.md` 附录或 `diff-matrix.md` 执行期章（**`diff-matrix.md` 亦为变更目录内落档副本**，更新随批次提交），供后续组与接续引用；条目须自包含（规则 + 依据 + 适用范围 + **连锁面**——该规则联动需同步的工件 / spec Scenario / 代码 / 测试清单）；推翻前裁定时前条标注「被 R<n'> 推翻」并对其连锁面重跑同步。
- **证据目录**：过程证据（验证输出、探针记录、复核报告）落 `/tmp/<项目>-evidence/`——易失、不入库、不进提交，**结论摘要进留痕**；`git status` 不得出现证据文件。

## 附：干净窗口验收（两步法）

并发构建/测试工具会使验证任务被**静默跳过**（SKIPPED）而整体仍报成功——**不得仅凭构建成功字样判定通过**。宣称批次验证通过前：

1. **确认无并发**：检查没有其他构建/测试进程在同时运行（如有，等待其结束或改窗口重跑）。
2. **确认任务真实执行**：验证输出中**无被跳过（SKIPPED）的验证任务**，且任务计数为 **executed** 而非命中缓存或空转（如 gradle 口径：`N actionable tasks: N executed`、SKIPPED 0）。

两步都过，该验收证据才可用于核对与勾选；不过则重跑验证。

## 附：验证与归档派发要点（自 SKILL.md §七 外移）

1. **先读目标项目声明的验证方式**：项目根 `AGENTS.md` / `CLAUDE.md`（其次 `README`、`package.json` scripts、`Makefile`、CI 配置）。项目声明优先于通用猜测。
2. **干净窗口执行验证**：可派 **fresh** 子代理执行（按 [routing.md](routing.md) 应用 `verify` 路由），提示自包含（项目路径、要跑的命令、期望结果、只读约束），回传命令与输出摘要；失败必须回传关键错误段。聚合多个命令时逐条记录退出码。**真实密钥只经参数/环境变量传入进程**（见上节真实凭据纪律）。
3. **验证不通过 → 不归档**。报告失败证据（命令、输出、涉及任务），问用户：修复（回到阶段 3 派修复任务）或明确跳过（记录为已知缺口，需用户显式批准后才继续）。
4. **归档前校验**：加载 `openspec-verify-change` skill 校验（任务全勾、spec 覆盖映射、design 一致性），发现缺漏（如勾选遗漏、delta 缺 Scenario）先修复重校——通过才归档。
5. **归档**：确认 `tasks.md` 全部勾选（有未勾选项不得归档），加载 `openspec-archive-change` skill 执行归档并同步主规格。
6. **归档单独提交一次**（`docs(openspec): 归档 <change>`），不与批次改动混提。归档报错 → 贴错误原文并停，不手工搬移目录。
7. **最终汇报六要素**：①变更名与工件路径；②验证证据（命令 + 结果摘要）；③归档位置（`openspec/changes/archive/...` 与同步后的主规格）；④后续宿主操作清单（需要用户在容器外做的事，如 skctl 登记、推送探测不可行时的 `git push`、以及命令仍不可见时的 `docker compose restart dsh` 兜底——推送先探测、可行则按用户指示代推，见 [failure-modes.md](failure-modes.md)）；⑤**沉淀回流清单**——执行期改动的工作流仓文件（skill 文本、工作流配置，含未提交项）逐条列明，交用户决定提交与方式，本流程不代提交；⑥**遗留待办**——worktree 闭环清单（入口 `/spec-done <变更名>`）、执行期临时偏离恢复点、预留编号，交用户决定收尾时机。

## 附：前置检查展开（自 SKILL.md §二 外移；仅展开 ①④⑤，编号与入口 §二 一一对应）

**②参数** 与 **③工作目录事实** 的正文留在入口 §二，此处不重复（防双源漂移）。

**①OpenSpec 根**：在项目根执行 `openspec list --json`，读返回的 `root` 字段。
   - `root` 为对象 → 项目已接入，继续。
   - `"root": null` → **未接入**。此时命令退出码非 0 是「未初始化」的答案，不是 CLI 坏了，不要重试。**绝不副作用创建** `openspec/`；向用户给三选一并等待答复：①`openspec init` 初始化本项目；②指定已注册 store（`openspec store list --json` 取 id，后续命令带 `--store <id>`）；③放弃本流程，按普通对话处理。
   - 若 `status` 报错以 `Declared in` / `Invalid store declaration in` 开头并指向本项目 `openspec/config.yaml`，说明项目通过 store 接入但该 store 本机无法解析——停下展示该错误的 `message` 与 `fix`，不要当作未初始化。

**④能力自检**：确认本 skill 所需的 `openspec-propose` skill 与**阶段 1.5 问答环节所需的 `grill-me` skill** 可加载；不可加载按 [failure-modes.md](failure-modes.md) 处置顺序处理（**先核对聚合层与 skctl 登记 → 会话内执行内置 `/commands-reload` 手动重扫 → 重启容器仅作兜底**）——其中 **`grill-me` 不可加载时降级为普通按轮提问并如实告知用户**（[failure-modes.md](failure-modes.md)）。**串行阶段 1 与并行阶段 1.5 第 4 步审视另需 `openspec-explore` skill**——它属「必须」级依赖：不可加载按同款处置顺序修复，仍失败**报告问用户三选一**（降级裸调研 / 改并行 / 终止），**不静默降级**。阶段 1 并行的两条规划线**不依赖任何外部调研 skill**：方法完全由 SKILL.md 第四节与 [../mode/parallel.md](../mode/parallel.md) 自包含定义（7 字段草案 + 独立性铁律）。

## 附：落档细节（自 SKILL.md §七 外移）

加载 `openspec-propose` skill，按其规程生成工件；输入 = 需求原文 + 并行（`line-a.md`+`line-b.md`+`diff-matrix.md`）/ 串行（`explore.md`+`decisions.md`）+ `code-design.md`（**第 5 材料**，阶段 1.7 产物；缺收敛留痕说明阶段 1.5 未做完、缺 `code-design.md` 说明阶段 1.7 未做完——先补做再落档）。

1. **生成四件套 + 复制两份规划材料**：生成 `proposal.md`、`specs/<capability>/spec.md`（delta，保持既有 capability 路径）、`design.md`、`tasks.md`。`design.md` **逐断言承载 `code-design.md` 的深度契约**（①触达面 ②证据锚 ③接口与数据形状 ④决策 ⑤逐组要点 ⑥假设与未决项），落档时**逐条核对**通过后再继续；**决策记录须含栈识别结论**（writer skill 名与证据，SKILL.md 第六节）。**随后把 `/tmp/spec-flow/<change>/code-design.md` 与 `diff-matrix.md`（串行 `decisions.md`）复制入 `openspec/changes/<change>/`**——**落档副本自此为权威**（执行期组段终形态化、R<n> 留痕与接续恢复读它；`/tmp` 侧原件不再维护；`explore.md`/`line-a.md`/`line-b.md` 不入库）。
2. **`tasks.md` 必须满足执行批次契约**（硬约束，后续执行直接依赖）：
   - 以 `## N. 组名` 编号分组表达**执行批次**；`N` 递增即执行顺序，**组间严格串行**。
   - **组即执行审核批次**：组内单任务是合法常态（单任务因依赖或写冲突单独成组时不强行拆并）；分组粒度**兼顾用户审核节奏**。
   - **组内任务互不依赖、可并行**：不得含互为前置、或写同一文件/同一目录的多个任务；有此情况必须拆到不同组。
   - 已加载 writer skill 时，任务拆分粒度**同时满足该 skill 的拆分规定**（**引名不复述数值**，防双源漂移）。
   - 每任务一行 `- [ ] N.M <一句可执行描述>；验证：<验证句>`；描述须**引用该任务触达文件在 `code-design.md` 触达面清单中的条目编号**（硬契约，「组内不写同一文件」据此机械化核对）。
   - **验证句**必须是第三方可核对的（具体命令、文件路径+断言、可观察输出），禁止「已实现」「工作正常」这类空话。例：`验证：python3 -c "import yaml;d=yaml.safe_load(open('x.yaml'));assert 'models' in d"` 退出码 0；或 `验证：grep -n 'spec-plan' agent/skills/README.md 命中且表格行存在`。
   - 单组任务数以映射文件 `parallelism`（默认 3）为上限，超出则拆组。
3. **分歧点提问**：工件之间存在取舍、design 有多种方案、需求有歧义时，一次问清；不自行拍板。**阶段 1.7 设计线上浮的待决项并入此处**（见「附：代码设计环节（阶段 1.7）」的上浮接线），不新开通道。
4. **校验**：`openspec validate <change> --strict`，必须退出码 0 且无 error/warning（此时变更目录已含两份材料副本，校验覆盖其存在）；不通过则修工件重跑，**不得带病落档**。
5. **落档即停（规划边界）**：本阶段只产出规划工件，**不写项目代码、不在同一轮继续执行**。
6. **展示摘要**：变更名、四件套与两份材料路径（`code-design.md`、`diff-matrix.md`/`decisions.md`）、任务组数与条数、每组并行度、验证句样例、风险与未决项（含阶段 1.5 收敛中未答的决策项）。
7. **落档工件单独提交一次**：只 `git add` 该变更目录 `openspec/changes/<change>`（含新建的 spec delta 与两份材料副本），提交信息 `docs(openspec): 落档 <change>`；目标仓库既有中文惯例时从惯例。
8. **固定收尾**：告知用户 `/spec-flow continue <change>` 随时接续执行——本流程不涉及执行模式、不派执行子代理（被 spec-workflow 委托时由其衔接：确认执行模式与引擎后继续）。
